# ADR-0013: كاش الكتالوج في Redis (cache-aside بمفاتيح ذات إصدار، والمخزون حيّ دائماً)
**الحالة:** مقبول (المتطلب 3، 2026-11-06)

## السياق
القياس "قبل" (`docs/performance/baseline.*`) أظهر أن قراءات الكتالوج (قائمة المنتجات، التفاصيل، التصنيفات) هي أغلب الحِمل، وأن مخزن الكاش `database` يجعل **محدِّد المعدّل نفسه** عدة استعلامات وكتابة في Postgres مع كل طلب HTTP (73,598 مسحاً و 12,125 تعديلاً لجدول `cache` في دقيقة واحدة). المطلوب (R3-5): كاش للبيانات الأكثر قراءة بسياسة واضحة للمدة والحذف، وتحديد ما لا يجوز تخزينه، مع شرط الإثبات: **تعديل منتج يظهر فوراً**.

## القرار
1. **Redis 8.6 خدمة مستقلة** (`redis:8.6.8-alpine3.23`) على `app-net` فقط، بكلمة مرور، بلا منفذ منشور وبلا تخزين دائم، `maxmemory 128mb` و `volatile-lru`. `CACHE_STORE=redis` لـ api و scheduler (الاختبارات `array`). الاتصال بـ phpredis بمهلة اتصال وقراءة 1 ثانية (القاعدة 6).
2. **ما نخزّنه (cache-aside، `App\Modules\Products\Cache`):**
   | المفتاح | المحتوى |
   |---|---|
   | `catalog:v{N}:categories` | قائمة التصنيفات |
   | `catalog:v{N}:products:{slug\|*}:{page}:{per_page}` | صفحة من القائمة (حتى الصفحة 50) + `total` |
   | `catalog:v{N}:product:{id}` | تفاصيل منتج موجود |
   كلها **بلا كتلة `stock`**: الكمية تُطلب حيّة من خدمة المخزون (GetStock دفعي واحد) مع كل قراءة وتُركّب فوق النسخة المخزّنة.
3. **الحذف عند التعديل بمفاتيح ذات إصدار:** كل مفتاح يحمل رقم إصدار الكتالوج `catalog:version`. أي `saved`/`deleted` لمنتج أو تصنيف — من أي مسار (API، seeder، أمر صيانة) — يزيد الرقم بـ `INCR` ذري عبر observer **بعد الـ commit** (`ShouldHandleEventsAfterCommit`). القراءة التالية لا تجد المفتاح الجديد فتبني من القاعدة. الإصدار المفقود (إعادة تشغيل Redis) يبدأ من الزمن بالميلي ثانية، فلا يعود إلى رقم قد تكون له مفاتيح حيّة.
4. **TTL = 10 دقائق** (`CATALOG_CACHE_TTL=600`): ليس هو ما يضمن الصحة (الحذف يضمنها)، بل حدّ لعمر مدخل لم يعد يُقرأ، وشبكة أمان لو فات حذفٌ ما.
5. **ما لا نخزّنه ولماذا:**
   | البيانات | السبب |
   |---|---|
   | **الكمية المتوفرة (stock)** | مصدرها الوحيد خدمة المخزون (القاعدة 5) وتتغير مع كل طلب؛ نسخة قديمة تعني عرض "متوفر" لمنتج نفد. تبقى حيّة دائماً |
   | طلبات الزبون ("طلباتي") وتفاصيل الطلب | خاصة بمستخدم واحد وتخضع لصلاحيات (BOLA)؛ كاش مشترك يخاطر بإظهارها لغيره، وحالتها تتغير بقرار المسؤول |
   | `auth/me`، تسجيل الدخول، refresh | بيانات هوية وجلسات؛ يجب أن يظهر تعطيل الحساب أو تغيير الدور فوراً |
   | الإشعارات | خاصة بمستخدم وتتغير مع كل حدث وقراءة |
   | البحث بالاسم `q` | نص حر = عدد مفاتيح غير محدود (يمكن ملء Redis به) |
   | الصفحات بعد 50 ومنتج غير موجود | نادرة القراءة؛ تخزينها يسمح لعميل يمرّ على أرقام عشوائية بملء الذاكرة |
   | أسعار المنتجات عند إنشاء الطلب (`ProductCatalog::findMany`) | لقطة السعر في الطلب يجب أن تكون من القاعدة مباشرة |
6. **تعبئة الكاش تقرأ من القاعدة الأساسية** (بعد إضافة نسخة القراءة، ADR-0014) لا من النسخة: وإلا قد تُخزَّن نسخة متأخرة تحت الإصدار الجديد.

## البدائل المرفوضة
- **حذف مفاتيح محددة (`forget`) عند التعديل:** تعديل منتج يغيّر كل صفحة تحويه وكل صفحة بعده (الترتيب بالأحدث) وصفحات تصنيفه القديم والجديد؛ تتبّع هذه المفاتيح هشّ، وفيه سباق: قارئ قرأ الصف القديم قبل الحذف ثم كتبه بعده.
- **Cache tags في Redis:** تعمل، لكن Laravel يحتفظ لكل tag بمجموعة مفاتيح تكبر دون تنظيف، ولا تعمل مع كل المخازن (الاختبارات).
- **تخزين المخزون مع TTL قصير:** حتى ثانيتان تكفيان لبيع ما نفد في العرض؛ والحجز في Spring هو مصدر الحقيقة على أي حال، فلا فائدة تستحق الخطأ المعروض.
- **كاش HTTP على nginx:** لا يعرف متى تغيّر المنتج، والمخزون جزء من الرد.

## العواقب
+ قراءات الكتالوج لا تلمس Postgres بعد أول طلب؛ ومحدِّد المعدّل صار في الذاكرة بدل صفوف مقفلة في القاعدة.
+ تعديل أي منتج يظهر في القراءة التالية مباشرة (اختبارات `CatalogCacheTest`, `UpdateProductTest`).
− أي كتابة على الكتالوج تُبطل كل الكتالوج (مقبول: الكتابة نادرة جداً مقارنة بالقراءة).
− Redis صار تبعية تشغيل: إن توقف تفشل الطلبات (محدِّد المعدّل نفسه فيه). لهذا له healthcheck و `depends_on`، ولا يحمل بيانات لا يمكن إعادة بنائها.
