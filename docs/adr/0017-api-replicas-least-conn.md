# ADR-0017: ثلاث نسخ من الـ API خلف nginx باستراتيجية least_conn، وحالة مشتركة لا محلية
**الحالة:** مقبول (المتطلب 5، 2026-11-20)

## السياق
R5-1..R5-4: ثلاث نسخ من التطبيق خلف موزّع حمل مع تبرير الاستراتيجية، وثلاثة عمّال على نفس الطابور، واستمرار العمل إذا توقفت نسخة، واكتشاف وإصلاح ما يتعطل عند الانتقال من نسخة إلى عدة نسخ، خصوصاً كل ما يُحفظ محلياً داخل النسخة.

طلباتنا غير متساوية في الكلفة: قراءة الكتالوج من كاش Redis تأخذ ميلي ثوانٍ، أما إنشاء الطلب فينتظر المخزن عبر gRPC ومعاملة في قاعدة البيانات، وقد يصل إلى ثوانٍ إن كان المخزن بطيئاً (مهلة 3 ث).

## القرار
1. **`api` بثلاث نسخ افتراضياً** (`deploy.replicas: ${API_REPLICAS:-3}`)، تتغير وهي تعمل بـ `make scale API=n`.
2. **`upstream api_pool` في edge** باستراتيجية **`least_conn`**: الطلب الجديد يذهب إلى النسخة التي لديها أقل عدد من الطلبات الجارية. `server api:9000 resolve` مع `resolver … valid=5s`: nginx يسأل DNS الخاص بـ Docker كل 5 ثوانٍ ويحتفظ بنسخة لكل حاوية، فالنسخة المضافة أو المعاد تشغيلها تدخل التوزيع دون إعادة تشغيل edge.
3. **الاستمرارية:** `fastcgi_connect_timeout 1s` و `fastcgi_next_upstream error timeout` (حتى 3 محاولات، خلال 10 ث) مع فحص سلبي `max_fails=1 fail_timeout=10s`: النسخة التي لا يُفتح معها اتصال تُتخطى ويُرسل الطلب لغيرها، وتُستبعد 10 ثوانٍ. nginx لا يعيد إرسال POST/PATCH/PUT وصل إلى نسخة، فلا يُنشأ طلب مرتين.
4. **العمّال:** `worker-mail` بثلاث نسخ (`MAIL_WORKERS`) على الطابور نفسه: RabbitMQ يسلّم كل رسالة لمستهلك واحد (`prefetch=1`)، والمعالج idempotent برقم الرسالة (ADR-0015).
5. **لا حالة محلية في النسخة:** كل ما تحتاج النسخ أن تتفق عليه مكانه مشترك:

| الحالة | مكانها |
|---|---|
| هوية المستخدم | JWT موقّع (لا sessions)؛ المفاتيح على volume `jwt-keys`؛ refresh tokens في Postgres |
| الكاش، حدود المحاولات، أقفال Idempotency، علامة read-your-writes | Redis (`CACHE_STORE=redis`) |
| **وضع الصيانة** | Redis (`APP_MAINTENANCE_DRIVER=cache`) — كان ملفاً محلياً |
| صور المنتجات | volume `product-images` مشترك بين النسخ و edge |
| الأحداث | RabbitMQ + جدول outbox |
| **أحداث WebSocket بين خوادم Reverb** | Redis pub/sub (`REVERB_SCALING_ENABLED`) — كانت داخل كل خادم |

6. **Reverb بنسختين** مع scaling عبر Redis، وعميل البث يحتفظ بعناوين DNS 5 ثوانٍ فقط (`CURLOPT_DNS_CACHE_TIMEOUT`) بدل 60.

## البدائل المرفوضة
- **round-robin (الافتراضي):** يوزّع العدد بالتساوي لا الحمل؛ نسخة تعالج طلبات بطيئة (مخزن بطيء) تستمر في استقبال حصتها فتتراكم الطلبات عندها. في الحمل المتساوي يتصرف least_conn كـ round-robin (رأيناه: 167/166/167).
- **`ip_hash` / sticky sessions:** لا نحتاج الالتصاق لأن النسخ بلا حالة؛ وكل حركة k6 والمستخدمين خلف NAT تأتي من IP واحد، فتذهب كلها لنسخة واحدة.
- **`random two least_conn`:** مفيد عند عدة موزّعات تتشارك النسخ؛ عندنا موزّع واحد يعرف العدّادات بدقة.
- **`set $upstream` مع resolver (الإعداد السابق):** يوزّع على عناوين DNS بلا ذاكرة للأعطال ولا استراتيجية؛ نسخة متوقفة تبقى تُجرَّب.
- **Health checks نشطة:** متاحة في nginx Plus فقط؛ الفحص السلبي مع إعادة المحاولة يكفي هنا.
- **Docker Swarm/Kubernetes للتوزيع:** أدوات صحيحة للإنتاج، لكنها خارج حدود Docker Compose المطلوب في المشروع.

## العواقب
+ مثبت بـ `make scale-load` (500 طلب: 167/166/167، و 0 فشل مع إيقاف نسخة) و `make demo-r5` و `make scale-problems` (كل مشكلة قبل وبعد).
+ زيادة النسخ أو إنقاصها لا تحتاج تعديل إعداد ولا إعادة تشغيل edge.
− edge نفسه نسخة واحدة: نقطة فشل وحيدة على هذا الجهاز (في الإنتاج: موزّع أمامه أو IP عائم).
− ميزانية اتصالات Postgres: النسخ × `PHP_FPM_MAX_CHILDREN` (3 × 16 = 48) + العمّال يجب أن تبقى تحت `max_connections` (100). ست نسخ تتجاوزها؛ الحل حينها pgbouncer أو تقليل `PHP_FPM_MAX_CHILDREN`.
− `scheduler` نسخة واحدة عمداً (المهام تُقفل بـ `withoutOverlapping` في Redis و `SKIP LOCKED`، لكن لا فائدة من تكرارها).
− قواعد البيانات و Redis و RabbitMQ نسخة كتابة واحدة لكل منها؛ تكرارها خارج نطاق هذا المتطلب.
