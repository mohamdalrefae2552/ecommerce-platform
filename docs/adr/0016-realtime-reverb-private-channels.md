# ADR-0016: التحديث اللحظي عبر WebSocket (Laravel Reverb) بقنوات خاصة موقّعة
**الحالة:** مقبول (المتطلب 4، 2026-11-13 — اختيار الإنسان: Reverb)

## السياق
R4-4..R4-6: الزبون يرى حالة طلبه تتغير لحظياً دون تحديث الصفحة **ولا يستطيع غيره متابعة هذا الطلب**؛ الطلب الجديد يظهر فوراً في لوحة المسؤول **ولا يدخلها إلا مسؤول**؛ التحقق من الهوية والصلاحية **قبل** الاشتراك في أي من القناتين. الـ API عندنا عديم الحالة (JWT في الذاكرة، لا sessions) ويعمل على PHP-FPM الذي لا يحمل اتصالات طويلة.

## القرار
1. **خادم WebSocket مستقل:** Laravel Reverb (بروتوكول Pusher) في حاوية `reverb`. المتصفح يصله عبر `edge` على نفس الـ origin (`/app/<key>`، ترقية WebSocket)، فلا CORS ولا تغيير في CSP (`connect-src 'self'`). واجهة النشر (`/apps/...`) **غير** منشورة عبر edge: يصلها العامل فقط من داخل `app-net` وبتوقيع السر.
2. **من يبث:** عامل `worker-realtime` يستهلك الطابور `realtime.orders` (ADR-0015) ويبث؛ لا يبث الـ API داخل طلب HTTP. نفس حدث RabbitMQ يغذّي البريد والبث، وتعطل Reverb لا يؤخر طلباً.
3. **قناتان خاصتان** (`Orders/Realtime/OrderChannels`):
   - `private-orders.{orderId}` — مالك الطلب فقط؛ حدث `order.status_changed`.
   - `private-admin.orders` — دور admin فقط؛ `order.placed` (بشكل `OrderSummary`) و `order.status_changed`.
4. **التحقق قبل الاشتراك:** القناة الخاصة لا تُفتح إلا بتوقيع. المتصفح يطلب `POST /api/v1/broadcasting/auth` (في العقد) مع الـ JWT؛ الـ API يتحقق من الهوية (guard) ثم قاعدة القناة (المالك/الدور) ثم يوقّع `socket_id:channel` بـ HMAC-SHA256 بسرّ Reverb الذي لا يغادر الخادم. Reverb يرفض أي اشتراك بلا توقيع صحيح. الرفض = 403 (والطلب غير الموجود كطلب الغير). حدّ 60 محاولة/دقيقة.
5. **تقييد إضافي:** `allowed_origins` = host التطبيق فقط (منع Cross-Site WebSocket Hijacking)، `accept_client_events_from = none` (المتصفح يستمع ولا ينشر).
6. **الواجهة:** `pusher-js` فقط (بلا laravel-echo). عند وصول حدث تُبطَل استعلامات TanStack Query فيُعاد جلب الحقيقة من REST (بصلاحياته)، فالحمولة المبثوثة إشارة لا مصدر بيانات. الخروج يقطع الاتصال.

## البدائل المرفوضة
- **SSE:** أبسط واتجاه واحد يكفينا، لكن كل اتصال يحجز عامل PHP-FPM، والتحقق من القنوات يُكتب يدوياً.
- **Polling:** ليس لحظياً ويضاعف الطلبات على الـ API.
- **البث من الـ API مباشرة (`ShouldBroadcastNow`):** يربط زمن الطلب ونجاحه بخادم WebSocket.
- **قنوات عامة باسم يصعب تخمينه:** معرّف الطلب ليس سراً؛ هذا BOLA على WebSocket.
- **خدمة خارجية (Pusher/Ably/Firebase):** بيانات الطلبات تخرج لطرف ثالث، ومفاتيح وحساب إضافيان بلا حاجة.
- **laravel-echo:** طبقة فوق pusher-js لا نحتاج منها شيئاً.

## العواقب
+ نفس نموذج الصلاحيات في REST (OrderPolicy) مطبّق على الاشتراك، ومثبت باختبارات `ChannelAuthorizationTest` وبـ `make demo-r4` (اشتراك مرفوض 403/401، وتوقيع مزوّر يرفضه Reverb).
+ التحديث يصل دون أن يحمل بيانات حساسة؛ القراءة الفعلية تبقى عبر REST.
− التوقيع صالح لعمر الاتصال: من فقد صلاحيته (تعطيل حساب) يبقى مشتركاً حتى ينقطع اتصاله؛ مقبول الآن (التوكن 15 دقيقة، والخروج يقطع الاتصال).
− Reverb نسخة واحدة؛ تعدد النسخ يحتاج `scaling` عبر Redis (المتطلب 5).
− حدث يُبث أثناء انقطاع اتصال المتصفح لا يُعاد؛ لذلك تعيد الواجهة جلب البيانات عند عودة الاتصال (`RESYNC`).
