# 00 — ملخص المشروع ومعايير القبول (مستخرج من عرض المادة)

> المصدر: عرض "منصة تجارة إلكترونية موزّعة ولحظية — المتطلبان الأول والثاني" (15 شريحة مع ملاحظات المحاضر).
> كل بند هنا مُرقّم ويُشار إليه من المهام والاختبارات. **لا يُضاف متطلب غير موجود هنا دون موافقة الإنسان.**

## الفكرة
متجر صغير يعمل كما تعمل الأنظمة الحقيقية. التركيز: الأمان والأداء والتوسع والمراقبة. الواجهة الأمامية **لا تُقيَّم تصميمياً**.

## الوظائف الإلزامية
| ID | الوظيفة |
|---|---|
| F-1 | تسجيل المستخدمين (تسجيل، دخول، أدوار) |
| F-2 | إضافة المنتجات مع صورها وعرضها |
| F-3 | إنشاء الطلبات |
| F-4 | إدارة المخزون |
| F-5 | متابعة حالة الطلب |

مسموح إضافة وظائف أخرى **بشرط أن تخدم متطلبات المشروع**.

## خارطة المتطلبات
| # | المتطلب | الحالة |
|---|---|---|
| 1 | الواجهات البرمجية والأمان | الآن |
| 2 | التواصل بين الخدمات | الآن |
| 3 | الأداء والتخزين المؤقت | لاحقاً |
| 4 | المعالجة غير المتزامنة واللحظية | لاحقاً |
| 5 | التوسع وتوزيع الأحمال | لاحقاً |
| 6 | المراقبة وتتبع الأعطال | لاحقاً |
كل متطلب يبني فوق الذي قبله؛ في كل مقابلة يُقيَّم الفريق على ما معه ويستلم التالي.

## المتطلب 1 — تصميم الواجهات البرمجية والأمان
**الهدف:** واجهة برمجية مرتبة وموثّقة، لا يصل فيها أي مستخدم إلا إلى ما يحق له.

### البنية
| ID | البند |
|---|---|
| R1-S1 | مشروع واحد مرتّب في أربع وحدات: **المستخدمون** (التسجيل، الدخول، الأدوار) · **المنتجات** (إضافة مع الصور، العرض) · **الطلبات** (الإنشاء، متابعة الحالة) · **الإشعارات** (كل ما يُرسل للمستخدم) |
| R1-S2 | كل وحدة في مجلد مستقل، **ولا تقرأ وحدة جداول وحدة أخرى مباشرة** (ملاحظة المحاضر) |
| R1-S3 | المشروع كاملاً يعمل بـ Docker في حاويات منفصلة |
| R1-S4 | اللغة والإطار حرّان |

### الواجهات البرمجية (REST)
| ID | البند |
|---|---|
| R1-A1 | إصدار في المسار (`/api/v1/...`) |
| R1-A2 | رموز حالة صحيحة (أمثلة المحاضر: 201، 404، 422) |
| R1-A3 | صيغة موحدة للأخطاء (كل الأخطاء بنفس الشكل) |
| R1-A4 | توثيق يمكن تجربته بسهولة (OpenAPI/Swagger أو Postman) |
| R1-A5 | الطلبات: إنشاء طلب · عرض طلب · تغيير حالة الطلب |
| R1-A6 | المنتجات: إضافة منتج مع صورته · عرض المنتجات · تصفية حسب التصنيف · تقسيم الصفحات |

### الأمان
| ID | البند |
|---|---|
| R1-SEC1 | مصادقة بـ JWT |
| R1-SEC2 | تحديد محاولات تسجيل الدخول (Rate limiting) |
| R1-SEC3 | ترويسات الأمان الأساسية |
| R1-SEC4 | دوران على الأقل؛ **المسؤول وحده** يغيّر حالة الطلب |
| R1-SEC5 | **الزبون يرى طلباته فقط** — لا يستطيع فتح طلب غيره بتغيير الرقم في الرابط (أشهر ثغرة: BOLA/IDOR) |

### الإثبات المطلوب في المقابلة
| ID | السيناريو | النتيجة |
|---|---|---|
| PROOF-R1-1 | زبون يحاول فتح طلب زبون آخر | يُرفض |
| PROOF-R1-2 | زبون يحاول تغيير حالة طلب | يُرفض |

## المتطلب 2 — التواصل بين الخدمات
**الهدف:** فصل إدارة المخزون في خدمة مستقلة يتواصل معها التطبيق عبر **gRPC** مباشرة.

### البنية
| ID | البند |
|---|---|
| R2-S1 | خدمة المستودع بلغة/إطار **مختلف** عن التطبيق الأساسي (Polyglot) |
| R2-S2 | لها قاعدة بيانات خاصة بها؛ التطبيق **لا يقرأها أبداً** |
| R2-S3 | العقد المشترك ملف `proto` يولّد منه الطرفان الكود |

### العقد (ثلاث عمليات)
| ID | العملية |
|---|---|
| R2-C1 | معرفة الكمية — كم بقي من هذا المنتج؟ |
| R2-C2 | حجز الكمية — احجز كميات منتجات الطلب |
| R2-C3 | إرجاع الكمية — أعد ما حُجز إذا فشل الطلب |

### التدفقات
| ID | التدفق |
|---|---|
| R2-F1 | إنشاء الطلب: **طلب واحد** لحجز كميات **كل** منتجات الطلب (كلها أو لا شيء). موافقة → يكمل التطبيق إنشاء الطلب. رفض → لا يُنشأ الطلب. **لا يُحفظ الطلب إلا بعد موافقة المستودع.** |
| R2-F2 | عرض تفاصيل المنتج: يسأل التطبيق المستودع عن الكمية ويعرضها مع التفاصيل |

### حالات الفشل (يُسأل عنها الطالب)
| ID | الحالة | السلوك المطلوب |
|---|---|---|
| R2-E1 | فشل الحفظ بعد الحجز | تُرجع الكمية المحجوزة إلى المستودع |
| R2-E2 | المستودع متوقف أو بطيء | مهلة محددة لكل نداء؛ لا ينتظر المستخدم بلا نهاية؛ رد واضح |
| R2-E3 | الكمية غير كافية | يُرفض الطلب برسالة واضحة |

### الإثبات المطلوب في المقابلة
| ID | السيناريو | النتيجة |
|---|---|---|
| PROOF-R2-1 | اختبار يرسل طلبات كثيرة **في نفس اللحظة** على منتج بقيت منه **قطعة واحدة** | ينجح طلب **واحد فقط** (Race Condition) |
| PROOF-R2-2 | إيقاف خدمة المستودع | عرض ما يراه المستخدم |
